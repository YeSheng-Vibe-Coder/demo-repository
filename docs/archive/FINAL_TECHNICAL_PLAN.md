## 一、规则如何生成，阈值如何确定

### 1. 三种来源分别负责什么

| 内容 | 来源 | 谁完成 |
|---|---|---|
| 应监测的行为 | AUSTRAC 指定段落，例如多方汇入、资金经过多个账户转移 | Agent 理解并引用段落 |
| 如何计算这种行为 | 我们预先写好的 fan_in / fan_out 查询模板 | 开发者实现；Agent 选择并映射字段 |
| 多少账户、多少小时才告警 | 主数据集验证部分及其标签 | 程序跑有限参数组合后选择，不能由 Agent 随口指定 |

AUSTRAC 通常只描述风险行为，没有给出这里要用的账户数和时间阈值。不能把数据校准出的数值写成官方要求。

第一版验证三个自动告警模板：

- **fan_in**：时间窗口内，多少个不同付款账户向同一账户转入。
- **fan_out**：时间窗口内，同一账户向多少个不同账户转出。
- **receive_then_send**：收到转账后，在指定间隔内再次向其他账户转出。具体支付范围统一限定为 ACH/Wire。

**循环转账是后续调查要验证的结构，不作为全表暴力搜索规则。** Agent 根据告警决定是否检查循环；结构是否存在由程序验证。第三个模板补充单一对手方链式转移的入口，并不证明转出资金就是刚收到的那笔钱。

### 2. 政策解析 Agent 具体输入和输出

输入只有三样：指定段落原文及编号、IBM 标准字段字典、三个允许的模板说明。

例如，输入“多个第三方向同一账户汇入”对应段落，输出草案：

```json
{
  "source_paragraph_id": "AUSTRAC-P02",
  "template": "fan_in",
  "account_field": "dst_key",
  "counterparty_field": "src_key",
  "time_field": "event_time",
  "window_hours": null,
  "min_counterparties": null,
  "status": "needs_calibration",
  "missing_context": ["账户是否属于不同自然人", "交易的经济用途"]
}
```

这里 P02 是我们的段落定位编号，不是监管规则编号。付款、收款账户键均为银行 ID 与账号组成的复合键。程序检查字段及模板合法、来源段落存在；缺字段就输出 unsupported。

用 Structured Outputs 约束输出结构。Agent 不写任意 SQL，也不接触洗钱标签；它完成的是“文字行为 → 支持的检测模板与字段”。

### 3. 阈值确定：明确采用验证标签校准

**是的，本方案使用 IBM 验证部分的标签选择阈值。** 这是离线的有监督校准，不是训练新模型；标签只给校准/评估程序，不给调查 Agent。

第一版固定搜索范围：fan_in / fan_out 各测试窗口 **24、48 小时**、对手方数 **3、5、10**，各 6 组；receive_then_send 测试最大间隔 **6、24、48 小时**。每个模板增加停用选项，三个模板联合比较告警量和覆盖效果；不适合的模板不强行启用。支付格式先限制 ACH/Wire，排除自己转给自己的交易；这些业务范围在看测试标签前固定。receive_then_send 的两笔均属于该范围，严格后续时间、不同交易 ID，支持交易对去重；新告警要求后续转出发生于当天。

每天结束时扫描一次，用此前 W 小时交易计算 distinct 对手方数。扫描时只看当时已发生的交易。币种不同不合计金额；这里的账户数统计不要求金额换汇。

阈值选择按同一口径完成：

1. 在验证日期每天收盘执行全部候选组合，按 `(焦点账户, 当天)` 合并模板间的重复告警；保留触发模板及支持交易。
2. 验证程序使用隐藏标签：若告警支持交易中，**当天新增且属于验证日期的交易**至少一笔标为洗钱，这个告警记为正例。更早历史交易的标签不能让今天的告警自动变正例。
3. 统计告警精确率；交易召回率则是“当天洗钱交易中，有多少出现在任一告警支持边里”，重复交易只计一次。支持边的分母/分子均限制在当日及相同支付格式范围。
4. 预设每日最多 **50 个合并告警**作为演示处理预算。该预算是项目假设，不是官方标准。
5. 在满足预算的组合中，先选验证交易召回率最高者，再以告警精确率、告警数较少作并列决胜。无可行组合则报告校准失败；有组合但效果弱也如实报告，不能到测试集继续改。
6. 将最终启用的规则、W/N/间隔、业务范围、版本和验证结果一起冻结，随后才运行测试。

注意：告警精确率与交易召回率的统计单位不同，**不把两者直接拼成 F1/F2**。也不能拿这里的标签指标证明每条 AUSTRAC 风险指标都有效：IBM 洗钱标签与监管指标的含义并非完全相同。

最终规则存两处：PostgreSQL 中的可查询规则记录，以及对象存储中的不可变版本 JSON。经 Zetaris 读回成功才标为可执行。当前尚未跑全量 IBM 校准，因此最终 W、N 不能提前填写。

## 二、数据怎么划分，告警从哪里来

### 1. 主数据与存储

下载同一版本的 `HI-Small_Trans.csv` 和 `HI-Small_Patterns.txt`，不下载整个约 41.6 GB 数据集合。

官方入口：https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml

- 交易原文件只读保存；按列位置把两个同名 Account 分别改为 src_account、dst_account，并生成交易 ID、源行号、复合账户键。
- 无标签规范化交易存对象存储，由 Zetaris 注册查询；准备不方便时先用 CSV，跑通后再换 Parquet。
- Is Laundering 与 Patterns 文件只放隔离的校准/评估存储，不注册到 Agent 可查询的数据源。
- AUSTRAC 段落、规则、案件、查询和证据引用存 PostgreSQL，由 Zetaris 联查。

完整交易及模式文件的单文件下载 URL：

```text
https://www.kaggle.com/api/v1/datasets/download/ealtman2019/ibm-transactions-for-anti-money-laundering-aml/HI-Small_Trans.csv
https://www.kaggle.com/api/v1/datasets/download/ealtman2019/ibm-transactions-for-anti-money-laundering-aml/HI-Small_Patterns.txt
```

下载后检查文件类型、哈希、表头及完整可读性。银行 ID 和账号保留为字符串，不丢前导零。发布时间和数据快照固定记录。

### 2. 明确的预设时间划分

采用该版本官方说明的主要活动区间 2022-09-01 至 09-10，按模拟数据原始时间划分，不随机打散交易。正式执行前先核对全表日期分布；主要区间以外的特殊尾部交易另列，不用它们的日期特征获取高分。

| 部分 | 交易时间区间，左含右不含 | 用途 |
|---|---|---|
| 历史预热 | 09-01 00:00 至 09-03 00:00 | 给最长 48 小时窗口提供历史，不计校准效果 |
| 验证 | 09-03 00:00 至 09-07 00:00 | 选 W、N，调试调查工具与动作提示 |
| 测试 | 09-07 00:00 至 09-11 00:00 | 冻结后运行规则、建立告警/案件并评估 |

验证按 09-03 至 09-06 每天结束扫描，测试按 09-07 至 09-10 每天结束扫描。执行条件为 `event_time < 当天结束时刻`；相同分钟的交易不能凭行号认定先后。

如果全表检查发现日期范围与官方主区间不符，先记录原因和新划分，再冻结；不能看过测试效果后移动切分点。

### 3. 测试案件与历史查询的区别

**是的，正式评估中的告警和案件全部从测试日期的扫描结果产生。** 验证案件只用于开发，不混入最终测试成绩。

但调查可以查询测试之前已经发生的历史：例如 09-07 的告警可以回查 09-05 的入账。这是正常的历史背景，不是泄漏测试答案。所有查询都受案件扫描时刻约束，不能提前看到后面的测试交易或标签。

初筛窗口 W 为校准出的 24/48 小时；调查回溯上限另设 **7 天**、最多 **12 跳**，用于检查更长结构，不等于初筛阈值。该范围和执行预算也在验证阶段确定后冻结。

主评估包含跨切分点的案件，但单独报告“历史延续案件”和“测试期首次可见案件”；不声称它们全是新账户泛化。Patterns 中横跨两侧的完整模式不能拆开后算两次独立成功。

测试规则跑全部测试日期。Agent 的运行预算先固定为合并后每天排名前 **10 个**，排名按命中模板数、不同对手方数、账户键排序，不看标签。展示规则全量效果，并对这批预先选定的 Agent 案件单独评估；不挑几个成功案件代替总体结果。

## 三、每查一步后怎么决定下一步，Meterless 怎么直接用

### 1. 调研结论：直接使用 Markovian 执行循环

Meterless 不只有 H-MEM。已检查实际源码：

- `Markovian.run({ stepFn })` 会反复调用我们传入的 stepFn，传递 carryover、限制最大步骤并记录过程。
- `HMEM.add(...)` 和 `HMEM.query(...)` 可以保存、召回带来源的调查摘要。
- 参考实现默认可用 mock generator，它不是开箱即用的金融 Agent，也没有自动执行 Zetaris SQL 的工具注册器。

**修订决定：Markovian 是主执行循环，H-MEM 是调查记忆；我们实现 stepFn 内的模型决策和工具执行。** 不再自己写一个外层 while 循环，另把 Meterless 仅当展示性记忆模块。

一个 chunk 对应一次动作选择及一次工具执行。模型根据“当前案件事实＋本步查询结果摘要＋可用工具”选择动作，不预写 A 查完一定查 B。

### 2. 下一步动作只有五种

| 动作 | 何时选择 | 实际执行 |
|---|---|---|
| inspect_account | 刚收到告警，或需要核查某个账户 | 查指定时间内入账和出账，获得方向及对手方 |
| expand_path | 已发现值得继续的转出/转入分支 | 查选定对手账户在约束时间内的交易 |
| check_structure | 目前证据可能形成循环/归集/分散 | 程序检查已取得交易的账户连接、时间及结构 |
| fetch_more | 当前结果被截断或仍有未读分页 | 拉下一页，不能把未看到当成不存在 |
| finish | 证据足够，或已无可查信息/达到预算 | 输出带证据的结论，程序校验引用 |

模型返回结构化动作，例如：

```json
{
  "action": "expand_path",
  "account_key": "bank_B:account_B",
  "direction": "outgoing",
  "after_transaction_id": "TX_123",
  "reason": "已观察到 A 向 B 转入，需要检查 B 后续是否继续转出",
  "evidence_ids": ["E_01"]
}
```

这是格式示例，不是实际运行结果。服务端从 TX_123 查得时间并约束后续查询，模型不能自行放宽时间上界，也不能伪造交易编号。规则字段、账户键和工具参数都由程序校验。

### 3. 用一个条件分支例子说明实际调查

以下 A/B/C 是说明用符号，不是我们补造的案件数据：

1. 规则发现 A 有资金分散现象，建测试案件。Agent 先 inspect_account(A)。
2. 查询若返回 A→B、A→C，Agent 根据时间和活动量挑一个未查分支，记录选择依据，再 expand_path(B)。
3. **若 B→D**：把 D 加入待查列表，继续检查 D；这条路径仍不证明循环。
4. **若 B→A**：调用 check_structure，核对两笔原始交易、方向和时间；验证通过才写“观察到循环结构”。
5. **若 B 无后续记录且结果完整**：这条分支停止，改查 C。若结果不完整，先 fetch_more。
6. **若候选闭环时间倒置**：不接受为按时间流转的循环，返回继续调查或证据不足。
7. 当相关分支查完或预算耗尽时 finish；报告列出已查与未查范围，不为了输出洗钱结论强行补完整链。

选择由模型完成，结构与数值由程序验证。模型可以修正判断，但所有新事实必须来自工具结果。

### 4. 每一步如何接 Meterless

具体调用示意及 SQL 模板见 [执行循环与查询示例](WORKFLOW_IMPLEMENTATION.md)。主流程为：

```text
Markovian 触发 stepFn
  → 从案件状态取已验证事实、已查窗口、待查账户和剩余预算
  → H-MEM 召回本案摘要（辅助，不替代原始证据）
  → 模型返回一个结构化动作
  → 我们的 Tool Router 校验参数、选择固定查询模板
  → Zetaris 执行 SQL 并取齐所需分页
  → 保存原始结果、query_id、交易引用及完整性
  → 更新案件状态，H-MEM 写入本步摘要和待查事项
  → stepFn 返回 STATE_CHECKPOINT，Markovian 开始下一步
```

完成并通过证据校验后返回 TASK_COMPLETE。Markovian 达到步骤上限并不代表案件已查清，此时结论是覆盖不足。H-MEM 按案件/快照/运行隔离，不能召回已揭示参考答案的历史运行。

Markovian 的 carryover 是压缩上下文，不能替代交易列表、visited 集合或精确查询覆盖范围；这些仍保存到案件状态。参考实现没有开箱即用的业务检查点恢复接口，重启时加载我们保存的状态，作为新 run 的初始上下文继续，而不是宣称原引擎自动恢复数据库任务。

## 四、Tool 如何查询，联表在哪里，结果怎么展示

### 1. 实际调用链

`模型动作 → Tool Router → 固定模板及校验参数 → ZetarisAdapter → Zetaris REST 查询 → 保存完整结果 → 本步观察 → 下一次 Markovian stepFn`。

模型不会直接调用数据库，也不会自己生成未校验的 JOIN。Zetaris 查询适配器负责打开查询、取分页、关闭查询；当前租户认证和路径仍需实际连通后固定。

### 2. 两种联表各有用途

| 查询 | 关联内容 | 用途 |
|---|---|---|
| 交易自关联 | A→B 的交易，与 B 后续转出的交易按复合账户键及时间关联 | 扩展资金链 |
| 跨来源联查 | 对象存储中的交易，与 PostgreSQL 的告警/规则/政策段落/证据关联 | 证明本案结论用了哪条政策、哪个规则版本、哪些原始交易 |

IBM 交易原本是一张表，不声称其天然是多个银行数据库。Patterns 文件是独立答案，**不能作为调查 JOIN 的一张表**。政策与交易通过实际生成的规则、告警和证据引用相连，不伪造共享业务键。

### 3. 页面只展示四项

1. **规则**：官方段落、生成模板、校准后阈值及验证指标。
2. **调查过程**：每一步要查什么、为何查、工具实际返回什么、判断如何变化。
3. **资金图与证据**：实际查询到的边，点击回到交易和 query_id；未访问的分支不画成已确认链路。
4. **结论与评估**：观察到的结构、涉及账户及时间、风险解释、证据缺口；调查完成后单独对照 IBM 隐藏模式和标签。

结论是“观察到符合某种模式的交易结构”，评估是“是否与发布方标注一致”。两者分开，不把读取标签当作自主调查。
