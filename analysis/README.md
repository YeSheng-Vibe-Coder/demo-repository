## 规则驱动闭环：真实运行验证

本轮已贯通规则告警、动态调查、逐笔标签校验、跨案件归纳、规则提议、编译、独立规则评估及实验版本登记。案件结束不调用 LLM 审批；独立模型评审仅在规则更新阶段使用。

### 实际业务链

冻结研究参考规则 → 在 Zetaris 已计算的开发特征上执行规则 → 15 条告警 → 按命中规则数、对手活跃度和固定 ID 排序（不读标签）→ 调查前 3 案 → 调查结束后逐笔核验检索及疑似交易 ID → 2 个模型正常结束案件用于跨案归纳 → NVIDIA Rule Proposer → 类型化规则编译 → 独立验证与 NVIDIA Rule Evaluator → 注册实验版本 → 同批验证监控检查。

调查期间：官方 Meterless Markovian/H-MEM → Python API → NVIDIA Planner 选择 Action / Replan / Finish → 固定 Zetaris 查询 → Observation → 下一轮。标签不进入调查模型或案件记忆。

起点是预登记的 research_reference，不冒充已经获批的初版规则。政策来源使用已核验 P02/P03；数值阈值是研究参数，不是 AUSTRAC 官方规定。

### 替代数据集筛选

日期：2026-10-20。目标：使用现成公开数据继续调查，不编造客户回复、身份资料或案件发展。

#### 首选：IBM Transactions for Anti Money Laundering（AMLworld）

官方入口：https://github.com/IBM/AML-Data

发布数据：https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml

论文：https://papers.neurips.cc/paper_files/paper/2023/file/5f38404edff6f3f642d6fa5892479c42-Paper-Datasets_and_Benchmarks.pdf

这是第三方公开合成基准，不是真实银行案件。与 PaySim 的关键区别是提供跨账户交易网络及模式级参考答案。建议从 HI-Small 开始，官方说明约 500 万交易、51.5 万账户，另外提供 HI-Small_Patterns.txt。

已实际下载并检查该模式文件：323,844 字节，370 个 BEGIN/END 配对完整的模式分组，含 3,209 条交易出现记录。类型：FAN-OUT 48、CYCLE 54、GATHER-SCATTER 51、STACK 43、RANDOM 41、BIPARTITE 49、FAN-IN 40、SCATTER-GATHER 44。每行有时间、双方银行/账户、收付金额和币种、支付类型及标签。精确统计和哈希见 ibm_pattern_inspection_EVALUATION_ONLY.json。

已看到一个包含十笔连续账户关联并回到起点的 CYCLE 分组，说明发布方确实提供了可还原链条，而不是只有单笔标签。其时间跨度为数日，不应预设所有模式都发生在 24 小时内；币种不同也不能直接加总金额。

建议工作流：隐藏 Is Laundering 和模式文件 → 在混合正常/异常交易中执行初筛 → Agent 查账户前后交易、扩展邻居、核对时间和币种、复原结构 → 输出可疑结构及证据 → 独立评估程序与发布方模式核对。

不要先把 Patterns.txt 交给 Agent，再把读出答案说成自主发现。发布方标注适合作为评估答案，不能充当运行时调查证据。也不能从循环结构直接推出某个人犯罪、非法集资或法院认定。

尚未下载完整 HI-Small_Trans.csv、验证模式文件与全表的对应关系或计算检测效果。官方元数据已保存。整套数据约 41.6GB（未压缩总量），不要直接下载全部；只取 Small 的两份文件。官方提示标称主要时间区间以外存在尾部交易且标签分布特殊，评估时必须检查时间捷径。数据许可 CDLA-Sharing-1.0，与 GitHub 代码许可不同。

AUSTRAC 匹配：多方汇入、资金经多个账户转移、分散和归集可部分实现。客户身份、受益所有人、经济目的和司法辖区风险不能仅凭银行 ID 或币种推断。

#### 备选：SAML-D

作者仓库：https://github.com/BOztasUK/Anti_Money_Laundering_Transaction_Data_SAML-D

数据：https://www.kaggle.com/datasets/berkanoztas/synthetic-transaction-monitoring-dataset-aml

作者和 Kaggle 官方元数据说明：9,504,852 笔合成交易，12 个特征，28 类 typology（11 正常、17 可疑），包含时间、双方账户、金额、支付类型、银行所在地及币种。它更适合比较正常/可疑交易模式，并支持有地点信息的分析。

#### 若必须使用真实交易：IEEE-CIS Fraud Detection

比赛官方数据说明：https://www.kaggle.com/c/ieee-fraud-detection/data?select=train_transaction.csv

数据含 transaction 与 identity 两张表，通过 TransactionID 联接；可用 DeviceType、DeviceInfo、邮箱域名及其他匿名特征展开多角度核查，训练数据有 isFraud 标签。但并非每笔交易都有 identity，匿名字段不能当作可核实的真实身份，也没有完整客服、争议和登录调查过程。

#### 若必须使用真实资金网络：Elliptic

发布方说明：https://www.elliptic.co/newsroom/elliptic-releases-bitcoin-transactions-data/

公开基准：https://www.kaggle.com/datasets/ellipticco/elliptic-data-set

真实比特币交易图，约 20 万笔交易，可沿图查上下游；包含 licit/illicit/unknown 分类。匿名化和特征解释限制较大，不含完整银行身份、合同或调查记录。适合链上资金关系调查；若沿用银行支付与 AUSTRAC 的现有演示框架，需要额外调整。当前仅做官方资料筛选，未下载验证。

#### 选择建议与验收边界

两到三天目标优先 IBM HI-Small；需要更丰富地点与模式字段时再核查 SAML-D。若用户排除所有合成数据，转向 IEEE-CIS 或 Elliptic，同时接受真实数据缺失与匿名化带来的调查边界。

这些候选都不等于公开司法案卷。完整且可验证的研究闭环是“发现 → 查询补充事实 → 复原模式 → 输出结论 → 对照隐藏参考答案”，不应声称还原了客户确认、警方调查或司法定罪。用第三方公开合成数据并如实标识、固定版本、隐藏答案和保留负例，区别于自己补写几个必然命中的案件。

### PaySim 与 AUSTRAC 风险指标：实际数据可行性检查

检查日期：2026-10-20（Australia/Sydney）。基于 Kaggle 官方完整 CSV，未抽样，未注入 mock 数据。

#### 结论

可以基于现有数据完成“官方指标 → 受限规则配置 → 查询异常 → Agent 调查 → 证据报告”的演示，但必须缩小业务承诺：这是交易风险调查原型，不能证明识别真实洗钱、账户接管或完整犯罪资金链。

优先展示：同类异常大额、多方汇入、证据不足时停止升级。后续小时转出可作辅助调查，不作为欺诈识别亮点。长期付款画像、分钟级交易、身份变更、国家风险和澳元阈值不适用。

本次已验证数据、官方文档及 Python 规则计算；尚未部署政策转规则 Agent，也未连接 Zetaris 租户或运行 Meterless。因此这是数据与规则可行性验证，不是整个产品已集成运行的证明。

#### 结论

本机 M1–M4 版本可认证、发现模型并执行 NVIDIA 请求，但当前配置不满足 AML 实验的固定模型、单次调用和严格预算要求。暂不将这个 Runtime 标记为可用于正式实验；不自动切换 provider，也不修改已安装应用文件。

#### 实测

- `/healthz`：200，`engine_ready=true`，供应商 `nvidia` 已配置。
- `/v1/models`：200，包含 `nvidia/nemotron-3.5-lightning-30b-a3b`。
- 请求：指定上述 Lightning 模型，`max_tokens=128`，`chat_template_kwargs.enable_thinking=false`，提示仅回复 OK。
- 响应：200，回复 OK，但返回模型 `nvidia/nemotron-3.5-super-vl-120b-a12b`；汇总输入 42、输出 142、总计 184 tokens。
- Console → Proof 的实际回执：应用 `aml-investigator`，路由 `meterless/auto`；质量处理包含 Lightning judge（解析失败、弃权）以及三个 reviser 的 debate；最终采用原回答。回执未签名。

#### 已定位的机制

以下来自只读检查本机安装包 `Contents/Resources/web/js/`，与实际回执吻合：

1. `engine/proxy.js` 的 `bindAppMode`：应用已有 mode 时使用它；首次无 mode 时继承并保存 cockpit mode，返回 `bound=true`。
2. `web/web-daemon.js`：`forceModel: bind.bound ? null : ...`。因此应用绑定模式时，客户端指定的具体模型不会强制固定路由。
3. `engine/proxy.js` 的 `passthroughFrom` 不包含 `chat_template_kwargs` 或 `reasoning_budget`；`web-daemon.js` 也未将它们另行放入请求参数。因此之前发送的关闭推理参数不能保证传到 NVIDIA。
4. `engine/providers.js` 的 NVIDIA adapter 从模型注册行或内部 `req.reasoning` 构造推理开关。不能把公开聊天接口接受 JSON 误认为所有字段都被转发。
5. `engine/orchestrator.js` 会执行质量处理，并累计多阶段的 `tokensOut`。`max_tokens` 不能作为整个逻辑请求的总输出预算；142 > 128 本身不能证明某一个 NVIDIA 生成请求超限。之前的这一判断需要收窄。

- 当前 Nightshift 路由标记为 `blocked_for_controlled_experiment`：HTTP 200 不等于满足模型与预算约束。

- 如果继续使用 Nightshift，需要先验证单模型路线、关闭额外 judge/debate/重试、推理控制透传，以及逐次供应商调用的完整用量。仅切换 Fast/Cheap 不能证明固定模型或预算生效。

#### 结论

实际数据支持从规则告警扩展出更多相关交易，也存在需要选择调查分支的案件。但本次程序策略没有超过固定图扩展，不能据此宣称 LLM Agent 提升了识别能力。

三方中的第三方是可复现的自适应程序策略，不是真实大语言模型。运行环境未发现常用模型接口的已配置密钥；本次没有调用模型、Meterless 或 Zetaris。因此这是数据及调查动作空间的可行性比较，不是三种已上线系统的优劣评测。

#### 数据与抽样

- 数据源为已下载完整 IBM HI-Small：5,078,345笔。检索图使用9月11日前的ACH/Wire，排除同账户交易，共699,795条边；不能将本报告结果外推到全部支付方式。
- 使用“账户收到款项后24小时内再次转出”的候选规则；24小时尚未校准。
- 9月7—10日产生33,524个账户/日告警；同账户同日仅保留首个触发，避免重复组合爆炸。
- 未读取标签抽取1,000个告警，随机种子20261020。它们是告警中的随机样本，不是全部交易的随机样本。
- 初始证据为触发出账及最近一次入账时刻的全部平行入账，不使用标签挑选。
- 案件查询截止为触发日结束，属于日终批量调查；不是在触发瞬间就知道后续交易。历史窗口为此前7天。
- 运行阶段不向策略暴露标签、模式名称或答案。所有查询完成后才读取标签及模式文件评分。

#### 比较方法

1. 仅规则：保留初始命中的交易，不做额外调查。
2. 固定扩展：按先发现先查询的顺序展开账户，参数固定，不按标签调整。
3. 自适应策略：根据已返回证据调整查询优先级，不访问未查询账户的真实度数。方向查询版本优先窄分支；全面查询版本优先已观察到的中转/汇集账户。

为防止工具范围决定结论，同时比较两种工具：

- 方向工具：追查入账之前的上游、出账之后的下游，最多5层，每次最多200行。
- 全面工具：查询账户历史窗口内全部入账及出账，可发现旁支，每次最多400行。

每个版本中固定与自适应使用完全相同的工具及上限；主比较每案最多12次调用。两类工具能力不同，不能直接将它们的耗时等同。调用数不包括共同的初始全量规则扫描及本地建图成本。

#### 随机1,000个告警的实测结果

| 方法 | 去重候选交易 | 其中带洗钱标签 | 完整取回的参考模式组 | 平均后续调用数 |
|---|---:|---:|---:|---:|
| 仅初始规则 | 1,998 | 27 | 1/10 | 0.00 |
| 固定上下游扩展 | 4,155 | 130 | 3/10 | 3.93 |
| 自适应上下游策略（程序） | 4,139 | 120 | 3/10 | 3.93 |
| 固定账户全面扩展 | 45,300 | 595 | 7/10 | 9.23 |
| 自适应账户全面扩展（程序） | 44,466 | 424 | 6/10 | 9.23 |

“候选交易”不是模型判定洗钱的交易。带标签数量是事后检索效果，不是推理过程已经证明犯罪；也不是分类准确率。跨案件去重指标与逐案累计指标不可混用。

本样本只有10个不同参考模式组满足严格评分条件：与初始证据相交，并且全部交易在本案时间及支付方式范围内。完整取回表示这些参考交易都在结果中，不表示系统已自主识别并正确解释了模式。全体带标签交易并不全部出现在模式文件中。

方向工具下，固定与自适应在991/1000个案件取得完全相同证据；70个案件用满12次调用。全面工具下，619个案件证据相同，531个用满预算；自适应在16个案件取回更多标签交易，在40个案件取回更少标签交易，其余不代表证据集合必然相同。这里出现分支选择空间，但不证明当前策略有效。

#### 对项目设计的影响

1. 保留IBM。它支持规则到网络调查，初始命中并未覆盖全部相关标签交易。
2. 图查询、时间约束、路径验证交给程序；不让LLM替代确定性计算。
3. 将LLM职责限定为基于证据提出调查问题、选择工具和分支、解释结果、指出无法核实的条件。需要真实模型与固定扩展在同一案件、工具和预算下比较。
4. 当前结果不足以宣传自主规划带来更高检出率。项目可以定位为可审计调查助手，下一阶段若要宣称自适应优势，应在预留数据上验证取证效率、覆盖、重复查询、错误调用和结论依据。
5. 不按这批测试结果继续调策略再复用同样样本报告泛化能力。这批已经查看的案件应视为探索样本；后续预留未看案件或另一份IBM数据做独立评估，并注意跨数据集实体和时间重叠。
